Cleaning AI Attribution from Git History

This procedure removes unwanted AI attribution, such as Co-Authored-By: Claude ..., from Git commit messages while preserving the substantive commit messages and code changes.

Important: rewriting Git history changes commit hashes. It can affect branches and tags, disrupt other clones, and require a coordinated update to GitHub. Work on a separate clone, inspect the result before publishing it, and do not force-push until you have verified exactly what will change.

These instructions concern attribution in commit messages. They do not remove AI-generated content from source files, change recorded author or committer identities, or establish who actually contributed to the work.

1. Inspect the repository

From the repository directory, run:

git status
git branch --show-current
git remote -v
git branch -a
git tag

Check that the working tree is clean and identify the branch you intend to update. If there are uncommitted changes, commit or safely preserve them before proceeding.

Inspect commit messages for unwanted attribution:

git log --all --format='%H %s%n%b' |
  grep -i -E 'claude|co-authored-by'

Review the matches. Decide exactly which lines should be removed. Do not remove legitimate authorship information or unrelated co-author trailers.

2. Make an independent backup

The safest approach is to work on a fresh clone and retain a separate mirror backup of the original repository.

From the parent directory of the repository, run:

git clone --mirror <REPOSITORY-URL> repository-backup.git
git clone <REPOSITORY-URL> repository-cleanup

Replace <REPOSITORY-URL> with the actual repository URL. Keep repository-backup.git untouched. It preserves the original Git references and history independently of the working copy.

If there are important local-only branches or commits that have not been pushed, preserve those separately. A fresh clone of GitHub will not contain them. 

cd repository-cleanup
git status
git branch --show-current
git remote -v

3. Install and check git-filter-repo

Ensure that git-filter-repo is installed:

git filter-repo --version

If the command is unavailable, install it using the instructions for your operating system before continuing.

4. Preview the proposed change

Inspect the full commit messages that contain the intended attribution. This command provides an initial search, not a complete audit of every possible attribution format. 

git log --all --format='commit %H%n%B%n---' |
  grep -i -B 1 -A 1 'co-authored-by:.*claude'

Examine the full messages of matching commits. The rewrite below targets lines beginning with Co-Authored-By: whose value starts with Claude, ignoring case and leading whitespace.

5. Rewrite the commit messages

Proceed only after confirming the backup exists and the matching lines are the ones you intend to remove.

Run this command from the cleanup clone:

git filter-repo --message-callback '
import re
return re.sub(
    rb"(?im)^[ \t]*co-authored-by:[ \t]*claude[^\r\n]*(?:\r?\n|$)",
    b"",
    message
)
'

This removes matching Claude co-author trailer lines from commit and tag messages processed by git-filter-repo. It preserves the rest of each message and does not remove arbitrary mentions of Claude elsewhere in a message.

The rewrite changes commit hashes. The tool may also remove the origin remote as a safety measure.

Do not add --force automatically. If git-filter-repo refuses to run because the repository does not meet its fresh-clone safety check, stop and resolve the issue. Do not bypass the check without understanding why it was triggered.

6. Verify the rewritten history

Search for remaining Claude co-author trailers:

git log --all --format='%H %s%n%b' |
  grep -i -E 'co-authored-by.*claude'

No output means this search found no remaining matches in the reachable history. It does not prove that every possible form of AI attribution has been removed.

Inspect recent commits:

git log -5 --format='%h %an <%ae>%n%B%n---'

Check that:

  • The intended attribution lines have disappeared.
  • The rest of each affected commit message remains intact.
  • Author and committer identities have not been changed.
  • Source files and substantive changes remain as expected.
  • Commit subjects, tags and other metadata are still appropriate.
git status
git branch -a
git tag

Compare the rewritten history with the original backup if anything looks unexpected. Do not publish the rewritten history until the results are satisfactory.

7. Decide which branches and tags to update

Do not assume that cleaning the currently checked-out branch cleans every branch or tag you intend to retain.

Identify the refs that were rewritten and the refs that must remain available. Check the repository's default branch, release branches and important tags.

A history rewrite can change commit IDs throughout descendant histories, even when the code changes themselves are identical. Signed commits and annotated tags may also need special attention because rewriting can invalidate signatures or change tag objects.

8. Prepare the GitHub update

Do not push yet. First inspect the remotes:

git remote -v

If origin was removed, restore it only after confirming the correct repository URL: 

git remote add origin <REPOSITORY-URL>

Then inspect the remote state:

git fetch origin
git branch -avv

Fetching allows you to inspect the current remote references. It does not make the rewritten history safe to publish.

Confirm which remote branches and tags need to be replaced. If other people use the repository, coordinate the rewrite with them first. They may need to re-clone or carefully reconcile their local branches.

9. Publish only after explicit verification

Rewriting a local repository and replacing history on GitHub are separate operations.

Before publishing, confirm all of the following:

  • The independent backup is intact.
  • The intended branches and tags have been identified.
  • The unwanted attribution is absent from the rewritten history.
  • The code and substantive commit messages are unchanged.
  • The remote repository is the correct one.
  • Anyone relying on the existing history has been informed.

If the rewrite is intended to replace a remote branch, use an explicit lease-based force-push rather than an unconditional force-push: 

git push \
  --force-with-lease=refs/heads/BRANCH:EXPECTED_OLD_COMMIT \
  origin \
  refs/heads/BRANCH:refs/heads/BRANCH

Replace BRANCH with the actual branch name and EXPECTED_OLD_COMMIT with the exact remote commit ID you verified before pushing. Do not copy the placeholder values literally.

This command refuses the update if the remote branch no longer points to the expected commit. It does not remove the need to review the proposed replacement carefully.

If the rewrite affects multiple branches or tags, handle each intended ref explicitly and verify the result. Do not use a broad push command without understanding which refs it will publish.

After pushing, fetch the remote state again and verify the updated branches and tags. Keep the backup until the rewritten repository has been checked and collaborators have reconciled their clones.

10. Prevent unwanted attribution from returning

First establish how the attribution is being added. Possible causes include an AI coding tool's commit configuration, a Git alias, a commit-message template or a local hook.

Inspect the relevant configuration and tooling before changing anything. Do not assume that a Git hook is responsible.

If attribution is being added automatically, change the setting that introduces it where possible. A local commit-message hook is an alternative, but it should be tested against ordinary commit messages and should remove only the specific unwanted trailer. 

git log -1 --format='%B'

A hook is not a substitute for checking the output, and local hooks are not necessarily shared with collaborators.

11. Final verification

Run the search again:

git log --all --format='%H %s%n%b' |
  grep -i -E 'co-authored-by.*claude'

Also check:

git status
git branch -a
git tag
git log --oneline -5
git remote -v

Confirm that the intended branches and tags exist, the working tree is in the expected state, and GitHub reflects the intended rewritten history if you chose to publish it.

A clean search only establishes that the searched attribution pattern is absent from the refs inspected. Other clones, old commits retained elsewhere, pull-request references, forks, cached objects and other attribution formats may still exist.

Summary

  1. Inspect the repository and identify the unwanted attribution.
  2. Create an independent backup and a separate cleanup clone.
  3. Preview the exact lines to remove.
  4. Rewrite the relevant commit messages.
  5. Verify that only the intended metadata changed.
  6. Check branches, tags, signatures and repository state.
  7. Treat publishing to GitHub as a separate, deliberate operation.
  8. Coordinate with collaborators and retain the backup.
  9. Identify and fix the mechanism that reintroduces unwanted attribution.
Principle: preserve the scientific and technical record, remove only the metadata you have deliberately identified, and never rewrite shared history without verifying the consequences.

This procedure removes a particular unwanted attribution; it is not intended to conceal provenance or change who actually authored a contribution. Removing an automatically inserted trailer while preserving genuine author and committer records is a much narrower operation than rewriting authorship itself.
