Fixing a Stale Claude Contributor on a GitHub Repository Homepage

If you have used Claude Code on a GitHub repository and later removed its Co-Authored-By entries from the Git history, you may find that Claude still appears as a contributor on the repository homepage.

This can be particularly confusing because GitHub's other contributor views may already be correct:

  • the current Git history contains no Claude attribution;
  • Insights → Contributors lists only the real contributors;
  • the REST Contributors API lists only the real contributors;
  • but the repository homepage still displays Claude in its Contributors widget.

This appears to be a GitHub-side stale-cache or indexing problem. There are multiple recent reports of this exact discrepancy.

The Workaround

The simplest non-destructive workaround I found is to temporarily change the repository's default branch.

1. Make Sure the Git History Is Actually Clean

First verify that the unwanted attribution has really been removed. 

git log master --format='%B' | grep -i 'co-authored-by.*claude'

If this produces no output, that particular attribution is no longer present in the master history.

You should also check GitHub:

Repository → Insights → Contributors

and, if desired, the Contributors REST API.

It is important to establish that this is actually a stale homepage display rather than an attribution that still exists somewhere in the repository.

2. Create a Temporary Branch from the Clean Default Branch

In my case the default branch was called master rather than main: 

git checkout master
            git checkout -b temp-cache-bust
            git push origin temp-cache-bust

If your repository uses main, substitute main accordingly.

You should now have a temporary branch containing exactly the same code and history as the clean default branch.

3. Temporarily Make the Branch the GitHub Default

On GitHub:

Repository → Settings → General → Default branch

Change the default branch from:

master

to:

temp-cache-bust

GitHub documents this as a normal repository operation; a repository with more than one branch can have any of them configured as the default branch.

4. Check the Repository Homepage

Visit the repository's main page.

In my case, this immediately changed the Contributors widget from:

doctorcbpower
            claude

to:

doctorcbpower

That was the key diagnostic result: the repository itself was clean; the stale contributor was associated with the homepage's cached contributor information.

5. Change the Default Branch Back

Once the homepage has refreshed, return to:

Settings → General → Default branch

and change:

temp-cache-bust

back to:

master

Check the repository homepage again.

If the stale contributor has disappeared, the cache refresh has worked.

6. Delete the Temporary Branch

Once you are satisfied that the homepage is correct: 

git push origin --delete temp-cache-bust
            git checkout master
            git branch -D temp-cache-bust

The final git checkout master is important if you are currently working on the temporary branch. Otherwise Git will correctly refuse to delete a branch that is checked out in your current worktree.

Why This Is Useful

This avoids unnecessarily rewriting the repository again or creating a new repository.

The important distinction is between Git history and GitHub's derived repository metadata.

If:

Git history             → clean
            Insights → Contributors → clean
            REST Contributors API   → clean
            Repository homepage     → stale

then rewriting the history again is unlikely to solve the actual problem.

Recent GitHub Community reports show the same pattern: the homepage contributor widget can disagree with both the Contributors graph and the REST API after history has been rewritten.

A September 2026 Community report specifically describes the default-branch toggle as a workaround for this stale sidebar, and another user reported that it worked. This is community-reported behaviour, not an official GitHub cache-invalidation procedure, so it should be treated as a workaround rather than guaranteed GitHub functionality.

If It Doesn't Work

Before taking more drastic action:

  1. Verify the Git history again.
  2. Check Insights → Contributors.
  3. Check the Contributors REST API.
  4. Check that no other active branch or tag contains the unwanted attribution.
  5. Give GitHub's contributor data some time to refresh.

GitHub's documentation says contributor displays and statistics can take around 24 hours to refresh after history changes, and directs repository owners to GitHub Support if they remain incorrect afterwards.

I would not immediately delete and recreate the repository merely because the homepage widget is stale. Repository recreation has consequences for:

  • repository URLs;
  • issues;
  • releases;
  • integrations;
  • stars;
  • forks;
  • DOI/archive links;
  • and other repository-level metadata.

In Short

If your repository is clean but GitHub's homepage still shows a former Claude contributor: 

git checkout master
            git checkout -b temp-cache-bust
            git push origin temp-cache-bust

Then:

GitHub
            → Settings
            → General
            → Default branch
            → temp-cache-bust
            → Update
            
            wait/check homepage
            
            → master
            → Update

Finally:

git push origin --delete temp-cache-bust
            git checkout master
            git branch -D temp-cache-bust

This is a relatively low-risk cache-busting workaround worth trying before considering repository recreation.
